# Building Crawlmouse: a live SaaS product, the stack, the numbers, and what it cost to ship

**Short answer.** Crawlmouse is a website auditing product we built and operate ourselves. It crawls a site, maps every internal link, grades the structure, and reports what AI crawlers can and cannot reach. Since its public launch on June 15, 2026 it has run 145 audits across 122 distinct sites, crawled 20,573 pages, mapped 1,318,736 links, logged 10,723 findings, and published 92 public reports. It runs on Next.js 15, Supabase, Inngest, Stripe, and Vercel, and it was built by the same two people who will build your software. This page exists because "we build SaaS" is a claim and a live product with a database you can query is proof. Numbers pulled October 9, 2026.

## Why we built it

Every website engagement we quoted in 2025 started with the same forty minutes: crawl the prospect's site, work out which pages were orphaned, which were buried, which anchors were stuffed, and whether a plain crawler (the kind behind ChatGPT, Claude, and Perplexity) could see what a browser could. We were doing it by hand with a desktop crawler and a spreadsheet. The product is that forty minutes, automated, with a grade a business owner can read and a findings list a developer can act on.

It also gave us something no agency portfolio provides: a product in production, with users we do not know, breaking in ways we did not predict, and a database that tells the truth about whether it works.

## What it does

A visitor pastes a URL. Crawlmouse fetches the site's pages the way a non rendering crawler does, reading the static HTML the server returns rather than running JavaScript. It builds the internal link graph, computes a structure score and an A to F grade, and lists the problems behind the grade: orphan pages, pages too deep to reach in a few clicks, anchors over optimized for one phrase, pages only reachable after JavaScript runs. A second module scores AI readiness: whether an llms.txt exists, which AI user agents the robots file allows or blocks, and how much of the site a plain crawler can actually read.

The result is a report the owner can keep private or claim and publish. A report becomes public and indexable only after the domain owner claims it, which is a deliberate consent gate and the reason there are 92 public reports from 123 completed audits.

## The stack, and why

- **Next.js 15 in a pnpm monorepo**: one repository with the web app (`apps/web`) and the crawl engine (`packages/engine`) as separate packages, so the engine can be tested and versioned without touching the UI.
- **Supabase** (Postgres, Auth, Row Level Security): audits, pages, findings, and public reports are relational data with an owner, and RLS enforces that a user sees only their own audits. The AI readiness result is a JSONB column on the audit row so the schema can evolve without migrations for every new check.
- **Inngest** for background jobs: a crawl can take minutes and must survive a browser tab closing, so each audit is a durable, retryable job with progress written back to the row.
- **Stripe** for billing.
- **Vercel** for hosting, previews on every pull request, and edge delivery.
- **IndexNow, llms.txt, and explicit AI crawler allows** on the product's own site, because a tool that grades AI readiness should pass its own test.

None of this is exotic. That is the point. A small business SaaS does not need a novel architecture; it needs a boring, well tested one that two people can operate.

## What we would do differently

Two things. We would have built the public report claim flow earlier, because unclaimed reports are value sitting in a table where nobody sees it. And we would have put the crawler politeness controls (honoring a robots rule aimed at our own bot) in the first release instead of the backlog; a tool that audits other people's sites should be the best behaved visitor they get, and that fix is next on the list.

## What this means for a business considering custom software

If you are deciding whether to commission a web app, a SaaS product, or an internal tool, the honest lessons from running one are these. Scope the first version to one job. Design the data before the screens. Ship to production early and read the logs. Expect the second and third releases to matter more than the first. And ask any firm you are considering to show you something it runs in production, not just something it delivered.
